## Du démarrage au résultat

**Notre système automatisé relie la préparation à l’exécution complète du parcours.** Il prend en charge les étapes techniques disponibles pour la configuration choisie, avec des réglages avancés accessibles lorsque vous en avez besoin.

| Étape | Ce que Novera prend en charge |
| --- | --- |
| **1. Démarrer** | Choisit une langue système prise en charge au premier lancement, puis conserve votre préférence. Présente les modèles de départ et les informations utiles sur le matériel. |
| **2. Préparer** | L’installation guidée propose texte, embeddings, image, musique, vidéo et agrandissement. Elle affiche composants, tailles et espace disponible avant votre validation, puis suit les téléchargements avec progression, pause/reprise et vérification SHA-256. |
| **3. Configurer** | Enregistre les modèles et leurs composants, prépare les profils adaptés et signale les dépendances à installer. L’embedding de recherche démarre sur CPU ; son placement CPU/GPU reste configurable. Le mode instrumental est activé par défaut pour les nouveaux profils musicaux. |
| **4. Comprendre la demande** | Le mode Auto oriente les demandes de création reconnues vers le texte, l’image, la musique ou la vidéo. Vous pouvez aussi choisir explicitement le mode et le modèle, local ou cloud. |
| **5. Exécuter** | La mémoire automatique attend les travaux actifs, libère les modèles inutiles et recharge les ressources nécessaires. Une série de 1 à 10 tâches s’exécute dans l’ordre, avec libération des ressources avant la suivante. Les fournisseurs cloud utilisent le compte et la configuration sélectionnés. |
| **6. Retrouver et réutiliser** | Enregistre les médias dans les dossiers système Novera, affiche les résultats et les durées disponibles, puis propose variantes, bibliothèque, copie, export ou partage système. L’envoi vers une autre application reste votre action. |

L’automatisation couvre les moteurs et parcours intégrés ; elle ne rend pas exécutable n’importe quel modèle du Hub. Matériel, composants installés et accès fournisseur déterminent les possibilités. Les dossiers, modifications de fichiers et commandes shell suivent les autorisations de la conversation.

## Hub et modèles compatibles

**GGUF, Safetensors classiques et quantifiés, ONNX et MLX** : explorez les modèles par usage et choisissez parmi les variantes compatibles avec le moteur et votre matériel.

| Famille | Prise en charge dans les sources | Conditions |
| --- | --- | --- |
| **GGUF** | Texte via llama.cpp ; composants image/vidéo selon le profil. | Architecture reconnue par le moteur embarqué. |
| **GGUF en plusieurs morceaux** | Une variante par série complète, taille cumulée, téléchargement et contrôle taille/SHA-256/en-têtes de tous les morceaux. | Numérotation standard ; télécharger 500 Go ne signifie pas que le modèle peut tourner sur ce PC. |
| **Safetensors classiques** | Dossier complet via Transformers, texte causal sur CPU ou NVIDIA CUDA. | Configuration, tokenizer et tous les fragments requis. |
| **ONNX Runtime** | Import local de graphes numériques/booléens et exports texte préparés pour GenAI. | Dossier complet validé ; pré/post-traitement spécifique à fournir ; [installation et limites](onnx-server/README.md). |
| **Adaptateurs LoRA / PEFT** | Importer une base complète avec son adaptateur local séparé dans le fournisseur Safetensors. | Base Transformers causale non quantifiée, identité correspondante, contrôle des tenseurs et mémoire cumulée estimée ; [installation et limites](transformers-server/README.md#local-lora--peft-adapters). |
| **FP8 LLM / ModelOpt** | Exécution CUDA native des exports FP8 par tenseur compatibles, Llama/Qwen2/Qwen3 denses. | Contrôle de l’architecture/des tenseurs et sonde réelle des kernels ; [installation et limites](transformers-server/README.md#modelopt-fp8-and-nvfp4-llms). |
| **NVFP4 LLM / ModelOpt** | Projections FP4 bloc 16 conservées compactées, GEMM CUDA natives ; voie distincte du NVFP4 image. | GPU Blackwell, dimensions/export compatibles et sonde réelle ; modèles de test non entraînés essayés sur RTX 5070. |
| **AWQ** | Checkpoints 4 bits GEMM non fusionnés. | NVIDIA CUDA et chargeurs optionnels GPTQModel/Transformers. |
| **GPTQ** | Configurations 2/3/4/8 bits, formats gptq/gptq_v2. | NVIDIA CUDA, GPTQModel et Optimum ; essai réel effectué en 4 bits. |
| **bitsandbytes** | 4 bits NF4/FP4 ou 8 bits INT8. | NVIDIA CUDA et dépendances optionnelles ; essais réels NF4 et INT8. |
| **EXL3** | Dossier Safetensors quantifié complet via ExLlamaV3 ; génération CUDA réelle testée. | GPU NVIDIA, environnement Python 3.12 séparé et architecture compatible ; aucun repli CPU. |
| **EXL2** | Chargeur ExLlamaV2 dédié ; streaming, annulation et déchargement testés sur GPU. | Backend CUDA Attention explicitement sélectionné pour l’environnement testé ; checkpoint complet du modèle et VRAM disponible suffisante requis. |
| **MLX** | Modèles compatibles sur Apple Silicon. | Moteur et plateforme MLX requis. |

Le Hub propose **LFM3-1.7B** comme recommandation LiquidAI épinglée pour les configurations compatibles, avec ses variantes Q4_K_M, Q6_K et Q8_0. Le modèle du premier démarrage reste celui indiqué dans la configuration guidée ci-dessus.

Filtrez les poids de **moins de 1 Go à 500 Go et plus**, puis triez par adaptation au matériel, taille, nouveauté ou téléchargements. Les résultats arrivent progressivement ; les filtres portent sur les modèles chargés et leur variante par défaut. Le diagnostic utilise la RAM/VRAM disponible, le contexte et les composants associés, sans compter deux fois la mémoire partagée du GPU.

Les quatre parcours quantifiés AWQ 4 bits, GPTQ 4 bits, NF4 et INT8 ont généré du texte sur une RTX 5070 Laptop avec de petits modèles non entraînés créés hors ligne. Cela valide le chargement et l’exécution, pas la qualité ou les performances de tous les modèles. **Ces nouveautés sont dans les sources : une recompilation et les dépendances adaptées sont nécessaires ; le binaire déjà installé ne se met pas à jour par cette modification du README.**

**Mesuré sur la RTX 5070 Laptop :** Qwen2.5-0.5B-Instruct, contexte 2 048, entrée 272 tokens, sortie 128 tokens, cinq essais après échauffement : décodage médian **GGUF Q4_K_M 402,7 tokens/s · EXL3 4 bpw 312,5 · EXL2 4 bpw 146,9**. Aucun gain de vitesse démontré ici face à GGUF. Quantification/calibration différentes et échec d’un contrôle arithmétique EXL3 : ces résultats ne constituent pas un classement général de vitesse ou de qualité. [Mesures et limites](deliverables/exllama-2026-10-30/validation.md).

**TabbyAPI** propose une connexion optionnelle à un serveur compatible OpenAI géré séparément, désactivée par défaut. Découverte du modèle EXL3 et streaming authentifiés ont été testés. Le chargeur ExLlama local géré par Novera reste un parcours distinct. [Installation ExLlama et connexion TabbyAPI](transformers-server/README.md#exl3-first-exl2-second--nvidia-execution).

Le tri par défaut favorise les sorties récentes à compatibilité et mémoire disponible équivalentes. Il ne remplace pas les modèles installés automatiquement.

[Installation Safetensors quantifiés](transformers-server/README.md#quantized-safetensors--source-integration-29-october-2026) · [Formats, priorités et validations](docs/SUIVI_MOTEURS.md)

Les sources ajoutent des **composants facultatifs gérés dans Configurations pour Windows x64** : environnements Python privés, profils CPU/CUDA épinglés, tailles et confirmation avant téléchargement, vérification, réparation et désinstallation. Les chemins personnalisés restent en options avancées. Les moteurs natifs GGUF gardent leurs composants existants ; le mobile et le cloud ne téléchargent pas les piles Python/PyTorch desktop. Trois profils privés CPU/export ont été testés avec des données de test synthétiques ; le mainteneur confirme le bon fonctionnement du desktop le 7 novembre 2026 ; les profils GPU et l’installation sur PC neuf restent à vérifier séparément en détail. [Profils et limites des tests](docs/REPRISE_COMPOSANTS_GERES_80_LANGUES.md). L’intégration de ces composants dans l’EXE est reportée.

## 120 langues et variantes d’interface

Mise à jour des sources du 6 novembre 2026 : 24 catalogues supplémentaires portent le total à 104. Ces traductions assistées restent à relire et à adapter par des locuteurs natifs. Ce lot prépare les catalogues et les README traduits ; une recompilation est nécessaire pour les inclure dans les applications installées.

Les **120 catalogues couvrent les 2 484 clés anglaises actuelles**, dans 15 espaces de noms : menus, configurations, réglages, aides et contrôles média. Les formes plurielles et la direction de l’interface suivent la langue choisie. La langue des réponses et des voix dépend séparément du modèle.

Cette couverture technique ne certifie pas la qualité linguistique : **relecture native et adaptation régionale restent nécessaires**. Consultez les langues, leurs noms et les limites connues dans le [guide des langues](docs/LANGUAGES.md) et le [rapport d’audit](deliverables/interface-audit-2026-10-29/RAPPORT.md).

## État du projet

La capture montre une application Windows compilée localement par le mainteneur. Les sources, les essais ciblés et les validations matérielles sont documentés séparément ; cela ne vaut pas validation de tous les modèles, plateformes ou comptes cloud.

Les compilations manuelles GitHub Actions sont activées pour les onze variantes de distribution. Consultez les [résultats de compilation et téléchargements des candidats vérifiés](docs/CI_DISTRIBUTIONS.md) ; la disponibilité est indiquée pour chaque plateforme.
