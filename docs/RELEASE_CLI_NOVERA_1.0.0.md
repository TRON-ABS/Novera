# CLI Novera — nom canonique et canal dédié

Préparation commencée le 2 novembre et poursuivie le 3 novembre 2026 à la demande du mainteneur : la commande, le nom de l'exécutable, l'aide, les identités terminal/ACP/MCP/RPC, les constructions et les archives doivent porter le nom Novera. Les attributions des dépendances et les références historiques aux versions publiées sont conservées.

Les exécutables canoniques sont **`novera.exe` sous Windows** et **`novera` sous Linux/macOS**. Le paquet Cargo est `novera-cli`. Les exemples et l'aide emploient `novera`. Les profils déjà situés dans `~/.novera` et les données Desktop ne changent pas d'emplacement. Les variables `NOVERA_API_KEY`, `NOVERA_BASE_URL`, `NOVERA_CUSTOM_HEADERS`, `NOVERA_EXPERIMENTAL_ACP`, `NOVERA_DATA_FOLDER` et `NOVERA_CLI_NO_UPDATE_CHECK` sont reconnues ; les anciens alias restent acceptés pour les intégrations existantes.

Les nouveaux ZIP portent une identité **formatVersion 2**, avec exactement l'exécutable canonique et `CLI-UPDATE.json`, liés à la version, à l'architecture, au commit et à l'empreinte du binaire. Le vérificateur refuse les archives d'identité historique au lieu de les relabeller.

La release canonique [v1.0.0-cli-novera](https://github.com/TRON-ABS/Novera/releases/tag/v1.0.0-cli-novera) est publiée, avec le canal **`latest-novera-cli.json`**. Les anciennes notes CLI signalent leur remplacement et la vitrine préparée oriente vers ces téléchargements. Les quatre releases historiques sont immuables : GitHub interdit de supprimer leurs fichiers individuellement ; les anciens liens directs restent donc accessibles. Douze fichiers CLI historiques ont été sauvegardés avec vérification de leurs empreintes ; aucune suppression n'a été effectuée. Les téléchargements Desktop sont conservés. Voir les [règles GitHub sur les releases immuables](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases).

Le canal distinct évite de proposer un ZIP `novera` aux anciens clients qui exigent un fichier `jan`. La première transition depuis un ancien exécutable est donc **manuelle** : extraire le nouveau ZIP dans un dossier distinct, lancer `novera --help`, vérifier les fournisseurs et discussions, puis adapter ses raccourcis/PATH. Aucun profil n'est effacé et aucun nouveau paquet ne s'installe automatiquement sous le nom historique.

Les paquets doivent être compilés, signés et vérifiés sur chaque hôte, avec essais de remplacement isolé et rejet d'un paquet altéré. La présence de la clé publique dans le binaire ou un test d'aide ne remplace pas ces preuves. Les résultats locaux, CI, publication et contrôle du canal public seront consignés séparément.

Les trois artefacts ont été contrôlés indépendamment : signature, architecture, format 2, aide canonique, empreintes et preuve de remplacement isolé. Les contrôles publics natifs Windows et Linux du run [41551771877](https://github.com/TRON-ABS/Novera/actions/runs/41551771877) passent et confirment le véritable canal de production, sans installation. Preuves : [reçus publics](release-evidence/cli-novera-1.0.0-2026-11-03/PUBLIC-CLI-VERIFIED.json). Le premier téléversement de ces reçus était absent car le chemin `.build` était exclu par défaut ; les reçus sont conservés depuis les journaux authentifiés, et le workflow est corrigé pour retenir explicitement ces seuls fichiers JSON et échouer s'ils manquent.

La publication remplace les deux CLI déjà distribuées : **Windows x64 et Linux x64**. Le créateur du feed exige les deux preuves natives correspondantes et refuse un candidat macOS dans cette sélection publique. La compilation macOS reste un candidat interne ; les distributions Apple restent suivies séparément.

Android reste suivi dans [RELEASE_ANDROID_1.0.0.md](RELEASE_ANDROID_1.0.0.md) ; le mainteneur reteste la recherche et la disposition des réglages avec le candidat 1000007. La vitrine conserve le statut d'essai et n'annonce pas une sortie Android validée.
