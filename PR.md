# fix(portable): keep Windows profiles and signed updates inside the portable folder

The existing ZIP runs the installed-app build, stores data in the Windows profile and retains the NSIS updater. Add a dedicated Windows portable feature: a marked Program/Data layout, private WebView/profile/cache/model roots, portable-only signed update endpoint and startup relocation of JSON/JSONL/YAML path references. Installed builds retain their original profile and update channel. Portable builds do not register deep-link handlers.

A native root launcher starts the application and can recover an interrupted Program swap. Its signed self-contained update payload validates all Program paths and hashes, obtains the exclusive profile lock, stages the complete runtime, swaps Program with rollback, preserves Data and restarts the app. Both ZIP and update executable are signed by the existing pinned key. The Windows-protected cloud secret store remains protected; another PC/account may require reconnecting. Optional Python environments can require repair after a move.

The dedicated native Windows workflow builds the portable app from source and reuses byte-verified engines from the immutable 1.0.0 x64 installer. It exercises real backend profile writes, relocation, Settings UI, signature verification, altered-payload rejection, same-version checks, complete Program restoration and synthetic discussion/model preservation. These are fixtures, not a claim about all models, USB devices or a transition between two public application versions.

Local validation so far: five portable support integration tests pass; native desktop with `--features portable` builds successfully against the production frontend; twelve targeted distribution/UI guard tests, Python/Node syntax, actionlint and diff checks pass. The signed native CI run and actual UI receipts remain pending. The application stays version 1.0.0. No portable availability is announced before publication.
